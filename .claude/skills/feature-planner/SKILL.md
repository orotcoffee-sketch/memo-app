# feature-planner

기능 하나를 **아이디어 한 줄에서 GitHub 이슈 등록까지** 진행한다. 이전 대화를 모르는 새 세션에서도 이 문서만 보고 끝까지 할 수 있게 절차를 자세히 적었다.

인자(`$ARGUMENTS`)가 기능 이름이다. 없으면 먼저 묻는다. 폴더 이름은 기존 `docs/features/tag/` 처럼 **영문 소문자-하이픈**(예: `memo-edit`)을 쓴다. 인자가 한글이면 영문 폴더 이름을 제안하고 확인받는다.

## 파일 위치

모든 문서는 `docs/features/<기능>/` 에 둔다.

| 파일 | 만드는 단계 |
|---|---|
| `spec-original.md` | 0 |
| `spec-fixed.md` | 1 |
| `prd.md` | 2 |

## 규칙

- **[멈춤]** 표시가 있는 곳에서는 **반드시 사람에게 묻고 답을 기다린다.** 답이 없으면 다음 단계로 가지 않는다. 내가 대신 고르거나 "진행하겠습니다" 하고 넘어가지 않는다. 사람의 답을 받은 뒤에만 파일을 쓰고 다음으로 간다.
- 인터뷰 질문은 **한 번에 하나씩** 한다. 여러 질문을 묶어서 던지지 않는다.
- 이 스킬은 **문서와 이슈만** 만든다. `src/` 코드는 건드리지 않는다.
- 사용자가 말하지 않은 결정을 문서에 몰래 넣지 않는다. 내가 정한 것은 "추천"으로 표시해서 물어본다.
- 커밋은 하지 않는다. 사용자가 요청할 때만 한다(형식: `docs(범위): 설명`).

## 절차

### 0. spec-original.md 만들기

`docs/features/<기능>/spec-original.md` 가 이미 있으면 읽고 1단계로 간다. (`spec-originial.md` 처럼 오타 이름이 있는지도 확인한다. 있으면 알리고 이름을 고칠지 묻는다.)

없으면 새로 만든다.
1. 기능에 대해 사용자가 이미 말한 내용(인자, 대화)을 정리한다.
2. 기존 문서 `docs/features/tag/spec-originial.md` 처럼 **제목 한 줄 + 한두 문장**으로 짧게 쓴 초안을 만든다. 사용자가 말하지 않은 세부 사항은 넣지 않는다. 세부 사항은 1단계 인터뷰에서 정한다.
3. **[멈춤]** 초안을 보여 주고 승인받는다. 고칠 부분이 있으면 고친 뒤 다시 확인받는다.
4. 승인되면 파일로 저장한다.

### 1. 스펙 확정 (인터뷰)

1. `spec-original.md` 를 읽는다.
2. 코드로 답을 알 수 있는 것은 묻지 말고 먼저 `src/` 와 기존 `docs/features/` 문서를 읽고 확인한다. (예: 메모 데이터 구조, localStorage 키, 기존 컴포넌트와 규칙은 `CLAUDE.md` 에 있다.)
3. 모호하거나 빠진 부분, 서로 부딪히는 부분을 찾아 질문 목록을 **속으로** 만든다. 보통 다음을 훑는다: 동작의 시작·끝 조건, 취소/저장 방법, 빈 값·긴 값·중복 같은 경계, 기존 기능(예: 태그, 개수 표시)과의 상호작용, 화면 표시 방식.
4. **한 번에 질문 하나**를 한다. 매 질문에는 아래 형식을 쓴다.
   - 질문
   - **추천 답** 과 그 이유 한 줄
   - 다른 선택지가 있으면 짧게 나열
5. **[멈춤]** 답을 받으면 다음 질문으로 간다. 사용자가 "추천대로" 라고 하면 추천 답으로 확정한다.
6. 질문이 모두 끝나면 확정된 내용을 `spec-fixed.md` 에 쓴다. 구조는 항목별로 **결정 + 근거**를 적는다. 쓰고 나서 요약을 보여 준다.

### 2. PRD 작성

`docs/features/<기능>/prd.md` 를 아래 5개 섹션으로 쓴다. 맨 위에 근거 문서(`spec-fixed.md`) 링크를 둔다. 형식 참고: `docs/features/tag/prd.md`.

1. **개요** — 기능이 무엇이고 왜 필요한지 2~3문장.
2. **사용자 이야기** — "~로서, ~할 수 있다" 형식으로 한 줄씩.
3. **기술 결정** — 아래 절차를 따른다.
4. **이번에 안 만들 것** — 범위 밖 항목 목록.
5. **용어 정의** — 문서에서 쓰는 용어와 뜻.

#### 기술 결정 절차

해결해야 할 기술 문제가 여러 개면 문제마다 반복한다.

1. **3가지 안을 표로 비교**한다. 기준(데이터 구조, 고쳐야 할 곳, 기존 코드와 비슷한 정도, 테스트 쉬움, 복잡도 등)을 행으로, 안을 열로 둔다. 안은 반드시 3개다. 추천 의견은 달 수 있지만 확정하지 않는다.
2. **[멈춤]** 표를 보여 주고 **사람이 안을 고를 때까지 기다린다.**
3. 고른 뒤에 아래 **4가지로 기록**한다.
   - **상황** — 왜 결정이 필요한가 (현재 구조와 제약)
   - **대안** — 비교한 3안 (표)
   - **결정** — 고른 안과 구체적인 규칙
   - **결과** — 장점과 단점(감수할 것)

### 3. "안 만들 것" 확인

**[멈춤]** `prd.md` 의 "이번에 안 만들 것" 목록을 **그대로 보여 주고** 사람에게 확인받는다. 빠진 것, 빼야 할 것이 있으면 고친 뒤 다시 확인받는다. 확인 전에는 4단계로 가지 않는다.

### 4. 이슈 분해

- **하나만 끝내도 사용자가 화면에서 볼 수 있도록** 기능 단위로 쪼갠다. "파싱 함수 만들기" 같은 눈에 안 보이는 내부 작업 단위로 쪼개지 않는다.
- 각 이슈는 **제목, 한 줄 설명, 완료 체크리스트**로 구성한다.
- 체크리스트는 **"~일 때 / ~하면 / ~된다"** 형식이고, 눈으로 확인할 수 있는 문장이어야 한다.
  - 예: `- [ ] 메모에 #업무가 있으면 메모 아래에 #업무 칩이 보인다`
- 이슈 간 순서(먼저 끝나야 하는 것)가 있으면 표시한다.
- "이번에 안 만들 것" 에 있는 내용이 이슈에 들어가지 않았는지 확인한다.

### 5. 이슈 등록

1. **[멈춤]** 이슈 목록(제목 + 체크리스트 전체)을 보여 주고 **확인받는다.** 수정 요청이 있으면 고치고 다시 확인받는다.
2. 승인되면 `gh issue create --title "..." --body "..."` 로 하나씩 등록한다. 본문은 설명과 체크리스트다. 순서가 있으면 본문에 선행 이슈 번호를 적는다.
3. 등록한 이슈 번호와 주소를 표로 보고한다.
