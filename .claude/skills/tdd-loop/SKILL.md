# tdd-loop

이슈 하나를 TDD 사이클 전체로 구현한다. 인자(`$ARGUMENTS`)가 이슈 번호다. 없으면 먼저 묻는다.

## 규칙

- **각 스킬이 사람에게 묻는 승인 질문(시그니처, 시나리오, 대조표 등)은 절대 건너뛰지 않는다.** 내가 대신 승인하거나 "진행하겠습니다" 하고 넘어가지 않는다. 답을 받기 전에는 다음 단계로 가지 않는다.
- 단계는 **순서대로** 하나씩 한다. 건너뛰거나 순서를 바꾸지 않는다.
- 어느 단계에서든 실패하거나 사람의 판단이 필요하면 **거기서 멈추고** 아래 "멈춤 보고"를 한다. 억지로 다음 단계로 가지 않는다.
- 각 단계는 해당 스킬/에이전트의 규칙을 그대로 따른다. 이 스킬이 규칙을 덮어쓰거나 완화하지 않는다.
- 커밋은 사용자가 요청하거나 `/create-pr` 이 요구할 때만 한다.

## 절차

### 0. 사전 확인과 브랜치

1. `gh issue view <번호>` 로 이슈를 읽고 **완료 체크리스트**(`- [ ]` 항목)가 있는지 확인한다. **없으면 멈추고** 사용자에게 알린다(체크리스트가 없으면 시나리오를 만들 수 없다. `/feature-planner` 로 이슈를 다시 만들거나 이슈에 체크리스트를 추가해야 한다).
2. 기능 이름을 정한다. 이슈 제목·`docs/features/<기능>/` 폴더 이름에서 찾고, 불명확하면 사용자에게 묻는다.
3. 커밋 안 된 변경이 있으면 알리고 어떻게 할지 묻는다.
4. 기본 브랜치(`gh repo view --json defaultBranchRef`; 이 저장소는 `master`)를 최신으로 맞춘 뒤 **`feat/<기능>-<번호>`** 브랜치를 만들어 이동한다. (예: `feat/tag-4`) 이미 있으면 그 브랜치로 이동해도 되는지 묻는다.

### 1~7. 단계 실행

아래 순서로 실행한다. 이전 단계가 끝난 것을 확인한 뒤 다음으로 간다.

| 단계 | 호출 | 끝났다고 보는 조건 |
|---|---|---|
| 1 | `/test-scenarios <번호>` | 시그니처·시나리오·체크리스트 대조표를 사람이 승인하고 `scenarios-<번호>.md` 가 저장됨 |
| 2 | `/tdd-red` | 모든 테스트가 "not implemented" 때문에 실패(Red) |
| 3 | `/tdd-green` | `남은 실패: 0` |
| 4 | `@ac-verifier` | 이슈의 모든 체크리스트 항목이 충족으로 판정됨 |
| 5 | `/tdd-refactor` | 테스트가 리팩터링 전과 같이 모두 통과 |
| 6 | `/security-review` | 보안 점검 결과를 사람에게 보고하고, 문제가 있으면 처리 방향을 확인받음 |
| 7 | `/create-pr` | E2E 통과 후 push, PR 생성(본문 `Closes #<번호>`) |

단계별 주의:
- **1단계**: 사람 승인이 세 번(시그니처 → 시나리오 → 대조표) 있다. 모두 받아야 한다.
- **3단계**: 같은 테스트가 5번 연속 실패해 멈추면 이 루프도 멈춘다.
- **4단계**: 충족하지 못한 항목이 있으면 멈추고 보고한다. 어떤 항목이 왜 부족한지 알리고, 2~3단계로 돌아갈지 사용자에게 묻는다.
- **6단계**: 심각한 문제가 나오면 7단계로 가지 않고 멈춘다.
- **7단계**: E2E 가 실패하면 `/create-pr` 의 규칙대로 PR 을 만들지 않는다. E2E 테스트 코드를 고쳐서 통과시키지 않는다.

## 멈춤 보고

멈추거나 끝날 때마다 아래를 짧게 알린다.

- **현재 위치**: `n/7 단계 (스킬 이름)` 에서 멈췄는지, 전부 끝났는지
- **이유**: 사람 승인 대기 / 테스트 실패 / 체크리스트 미충족 / 보안 문제 / E2E 실패 등
- **끝난 단계**: 완료한 단계 목록과 각 결과 (예: `3단계: 남은 실패 0`)
- **다음에 필요한 것**: 사용자가 해야 할 일(승인, 결정)

맨 마지막 줄에는 `진행 상황: n/7` 을 쓴다. 전부 끝났으면 PR 주소도 함께 알린다.
